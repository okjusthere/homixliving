# Administrator login email management

Open **Admin → Agents → Emails** beside a person, or **Edit → Manage login emails**. Existing primary and secondary addresses are shown together. Check another email, confirm it belongs to this person, then link it. The new alias also appears in the searchable agent list.

An administrator's confirmation grants access to the existing person record. Google still verifies control of the mailbox during sign-in. Primary email, account status, roles, website profile and business records are unchanged; aliases of an administrator share that person's administrator access, explicitly disclosed before confirmation. This operation does not send email or change EmailService.

The server checks email-address records, legacy primary addresses, stable Google identities (including disabled identities), unexpired self-service requests and reserved `ADMIN_EMAILS`. An email owned by another person record offers **Review and merge account**. Start from the account with the correct website profile: that account, its primary email, details and access remain canonical.

The merge preview names both accounts, lists incoming email addresses, counts Google identities and activity references, and shows the website profile being retained. An administrator must confirm that both accounts belong to the same person. The merge moves login identities and simple activity history, snapshots the duplicate in `agent_merge_history`, removes the duplicate person record and writes an audit entry in one transaction. Existing disabled or unverified identities remain disabled/unverified. Existing sessions on the removed account may require signing in again.

Only ordinary duplicates without business obligations are eligible. Administrator accounts/configured emails, inactive sources, inactive targets, existing contracts, payments, billing customers, team terms, pending email verification and additional website profiles block the merge. All foreign keys are discovered from the database; any reference outside the explicit identity/activity allowlist also blocks, including future schema additions. Birthday/anniversary records, posters, finance and legal ownership therefore require separate review if they exist on the duplicate. Website data is read for validation and is never changed by this operation. A missing website table fails closed. **Website profile merge is not account merge.** Resolve two website profiles in the website roster before merging their accounts.

Only current active administrators can use the API. Mutations require a matching Origin and bounded validated input. Alias assignment confirms the target's administrator status; account merge binds confirmation to a revision of both accounts, identity rows, website links and reference counts. Rows are locked and eligibility is rechecked during commit. Changes after preview require a new preview. No new migration, credentials or environment variables are required.

API: `GET /api/admin/agents/:id/emails` lists addresses. `POST` with `action: preview` checks ownership; `action: link` requires `confirmed: true` and `expectedAdmin`. `merge-preview` takes `sourceId`; `merge` also requires its returned `revision` and `confirmed: true`. The URL always identifies the retained account. New aliases use `source=admin_assigned`; migrated addresses retain their verification provenance. Primary changes and revocation are outside this action.

Validation: clone the Portal schema into a disposable local database named `homix_admin_identity_test`, then run `npm run test:admin-agent-emails:db` with its `DATABASE_URL`. The test deliberately rejects audit writes to prove alias and merge rollback, exercises concurrent ownership/merge races and future business references, and refuses other database names or remote hosts. Browser checks additionally cover ordinary/stale-admin denial, Origin and confirmation requirements, successful linking/merge, alias search, conflict display and mobile layout.
