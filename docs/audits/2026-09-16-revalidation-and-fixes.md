## F1：为什么“页面没显示”仍要修

旧代码把完整 Agent 数据从数据库查询出来再送给浏览器，包含内部备注、邮箱变更 token 哈希、电子签约标识等。页面只显示姓名，不能阻止浏览器收到其余字段。修复前，合成资料的真实接口测试实际收到完整 56 个字段，因此这不是仅凭猜测列出的风险。

现在数据库查询本身就只选择 `id`、显示姓名、分佣比例和持牌公司四个字段。租赁和买卖的列表、详情、保存后的响应统一使用这个边界，保留 Preferred name 的现有显示逻辑。普通成员、团队长、管理员都走相同的交易参与者字段白名单；管理人员若需完整档案，仍通过专门的管理接口。

验证覆盖四个 GET、两个 PUT、普通成员／团队长／管理员及无关人员、未登录、停用账号。修复前失败，修复后通过。

## F2：停用是停用，配置管理员也不能自动恢复账号

后续 main 已经让业务守卫重新读取账号状态，不能再笼统说“所有旧 JWT 都绕过停用”。但 OAuth 登录和会话刷新仍会把配置中的已有管理员重新设为 active；原角色协调也只授予、不撤销权限。

用户在部署前进一步明确：只有配置中的四个邮箱实际登录才具有管理权限。因此 JWT／session 新增独立的 `loginEmail`，只在已验证的 Google 登录时写入；业务主邮箱仍用于档案和账务。管理权限要求账号在职、本次登录邮箱仍属于该账号，且这个邮箱本身位于 `ADMIN_EMAILS`。同一账号的其他登录别名不会继承管理权限，也不会因为一次普通别名登录而撤销该账号其他合法管理员登录。已有 pending／inactive 账号不会因登录恢复 active；新管理员首次建立档案的引导行为保留。旧会话没有实际登录邮箱，管理权限会拒绝放行，需要退出后重新 Google 登录。

进一步检查调用链后，修复了内容模块重新采用原始数据库管理员标记的问题，以及停用／撤权管理员仍出现在运营通知名单的问题。角色变更写入审计记录。

**部署核对：** 截图中的四个管理员账号均在职且无额外数据库管理员；生产 `ADMIN_EMAILS` 原来仅有三个邮箱，缺少用户明确批准的第四个地址。按用户指定名单补齐为恰好四个，并复核。仅有历史 `isAdmin=true` 或同账号其他别名，不再单独授予管理权限。

## F3：保留收款凭据，并让出错结果可信

发票删除现在同时检查发票状态、发送记录和佣金账务。普通参与者和管理员都不能通过直接删除抹掉已使用的财务记录；管理员撤回收款仍走原有流程，已发放佣金时仍被拒绝。

删除、收款登记、撤回收款复用交易锁，并在等待结束后重新读取发票。这样不会出现“等待时发票已删除，随后还生成收款记录”。租赁删除也检查过：已冻结佣金的交易不能删；未冻结交易删除只解除发票关联，保留发票与发送历史。

发送流程增加了开始记录，发送中的发票不能删除，同一时刻的第二次发送返回冲突。发送结束或失败只更新发送状态，不能覆盖过程中已经登记的收款。

邮件失败分三类处理：

1. PDF 准备失败、邮件服务商明确拒绝等确定未发送的结果，记录失败，可修正后重试。
2. 网络超时、服务商 5xx、响应损坏或缺少确认编号，不能证明没发出去，保留“发送中／待确认”。
3. 服务商已确认成功、但随后数据库保存失败，同样保留待确认，不误报为可直接重发的失败。

管理员可在开始发送两分钟后，对照邮件服务商记录，在发票发送历史中选择“已核实发送成功”或“已核实未发送”，填写核实依据。这个操作不发送邮件，结果和管理员审计在同一事务保存，也不会撤销已收款事实。两个人同时处理只有一次成功。

前端也改为尊重删除接口的错误：失败时保留页面并说明原因，不再弹出虚假的删除成功。发票加载失败可以重试；中文界面也显示服务端的具体恢复说明。

## F4／F5：支付通知到达不等于业务处理完成

旧实现首先登记事件，重投时只看“事件行已存在”，无法分辨第一次究竟成功还是中途退出。现在新增 `completed_at`，业务处理成功后才标记完成。处理异常、锁竞争或连接中断不会伪造完成，Stripe 可以重投。

Checkout、订阅、发票通知优先按同一本地订单串行处理。持锁后重新向 Stripe 查询当前对象，不拿迟到通知里的旧快照覆盖新状态；获取失败时返回失败等待重试，不退回使用旧快照。查询前后都验证该对象属于 Homix。

真实收入仍按 Stripe 发票登记，每张发票的奖励仍幂等；旧账期真实收入不会丢弃，也不会把当前订阅从欠款／取消改成旧状态。付款日期只向前更新。

锁使用额外的最多一条连接，避免四个回调占满现有四连接池后互相等待。拥挤时返回 503；回调方重试。测试既模拟了整个处理进程被杀，也模拟了只有锁连接断开而 Node 仍在运行的情况，后者在外部读取返回后停止继续写账／履约。

**仍有现实边界：** 不能撤回已经发出的第三方 HTTP 请求，数据库与 Google Workspace 之间也没有分布式原子提交；外部创建结果未知时继续走已有的人工核实状态。付款后人为改成不兼容方案，再收到同一旧发票的新事件，仍可能需要人工对账；本次未把所有方案结算重构成新的账本。不能据本轮测试承诺任何供应商操作绝对只执行一次。

## F9：文件重试不应造成两份记录

修复前，真实并发登记返回两次 201，证明本轮 main 仍存在问题。现在注册和删除按同一 `objectKey` 共用数据库事务锁：相同文件、相同交易和元信息的重复登记返回同一记录；冲突元信息返回 409。

对于历史重复引用，删除其中一条仅删对应记录，最后一个引用删除时才删除 R2 对象。R2 删除失败会回滚数据库删除。注册失败保留上传对象供重试，避免把可能已登记成功的文件误删。

本次不批量清理历史数据。应用路由锁不能限制手工 SQL；R2 删除成功后数据库提交失败等极端跨系统故障仍需处理，后续可用删除任务表和孤立文件清理进一步改善。

## 上线顺序与恢复

1. 核对 `ADMIN_EMAILS`，保留应有的管理员身份；准备当前部署和数据库备份。
2. 先执行 [Stripe 增量迁移](/Users/weizhengle/Downloads/vibecoding/homixliving/db/migrations/20260916-stripe-webhook-completion.sql)，再部署应用代码。不要用带业务种子的 `db:seed` 代替生产增量迁移。
3. 迁移只回填旧代码明确关联订单的事件。迁移后至部署完成期间，旧版本刚处理成功而写有订单关联的事件也按成功兼容，防止切换窗口重复执行。旧空关联行保持未知，不自动批量重放；需要恢复时，在 Stripe 核实对应事件并重新发送。超出自动重试期也需人工重新发送。
4. 部署后用批准的测试账号验收登录、停用、租售查看、发票草稿／收款保护、文件重试和一笔受控支付通知，并观察 5xx／503 和待确认邮件。
5. 需要回滚应用时可以保留新增 nullable 列；不要删除历史事件、重置所有完成标记或批量重放以“修复”问题。

F6“取消交易后是否允许结算”需要业务规则；F10 通用 Checkout 多次创建是否需要进一步统一幂等仍待单独动态核实。本次没有把这两项写成已修复，也没有擅自改变取消交易的结算政策。
